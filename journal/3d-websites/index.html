Creative development / Three-dimensional web

3D websites.
The secret is the interaction.

A floating object gets your attention. The way it responds makes you stay. Here’s how I’d approach that kind of website, and what’s already happening inside this portfolio.

A model alone won’t save the page.

Drop a rotating object into a weak layout and you still have a weak layout. The references here work as compositions: strong type, a clear subject, convincing materials, and enough space for everything to read.

Then comes the interaction. A small response to the pointer. A change of viewpoint as you scroll. Light that helps you understand the shape. Those are separate decisions, and they need to support the page’s purpose.

A screenshot only shows the finished frame. It cannot tell us whether a site uses a live 3D model, a rendered image, a video, or a particular JavaScript library. The notes below describe what’s visible; they aren’t claims about those sites’ source code.

01 / Read the references

Three different ways to use depth.

Jinto: let the product interrupt the type. The large lettering creates the structure; the container overlaps it and becomes the focal point. Start with that relationship before adding motion.

Chirpley: give the subject a personality. The orange character and stretched red type carry the frame. The soft shading separates the bird from the flat background without making the whole interface look like a 3D scene.

The robot reference: make the layout do some work. A detailed metallic subject sits against a quiet grid and oversized numerals. The surrounding information stays small and orderly. The contrast creates depth before anything moves.

02 / Choose the right tools

Build the effect you actually need.

  • HTML and CSS: keep headings, links, and buttons in the page. Layered images and perspective transforms may be enough for a single fixed viewpoint.
  • Three.js: use a scene, camera, geometry, and materials when you need a real change of viewpoint or an interactive model. It handles much of the rendering machinery you would otherwise write yourself.
  • GSAP and ScrollTrigger: useful for coordinating sequences and connecting animation progress to scroll. They control movement; they don’t supply your model or art direction.
  • Custom WebGL: useful for a specific shader effect, like the liquid mark on my homepage. It gives you control and makes you responsible for the rendering details.

My local agent toolkit also includes Animaxxing for DOM motion recipes and Animaxxing WebGL for shader and image effects with a normal image fallback. Those are optional instructions for a compatible coding agent, not libraries already running on this portfolio. Check the skill’s actual availability and dependencies before asking your agent to use it.

For design direction and review, start with my four AI web design skills. Get the composition right before adding another animation tool.

03 / Inside this portfolio

What the source actually does.

This portfolio’s opening mark uses WebGL 2 and custom shaders. It does not use Three.js or GSAP. Pointer input feeds a fluid simulation, the shader draws the liquid surface, and scroll progress controls the transition into the portfolio.

  • main.js connects pointer input, scroll progress, rendering, and the fallback.
  • fluid.js updates the fluid field; liquid-shader.js samples it and shades the mark.
  • portfolio-velocity.js gives visible text and media a small scroll-driven drift. It stops when the page is hidden or reduced motion is enabled.

One small detail from the renderer: it limits resolution instead of blindly rendering every screen at its maximum pixel density.

const width = stage.clientWidth;
const height = stage.clientHeight;
const dpr = Math.min(devicePixelRatio || 1, 1.5, Math.sqrt(1200000 / (width * height)));
canvas.width = Math.round(width * dpr);
canvas.height = Math.round(height * dpr);

This is an excerpt from main.js, not a standalone renderer. The limits are this project’s choices, not a universal performance target. The opening also draws a still fallback and keeps it when WebGL is unavailable or reduced motion is requested.

04 / A practical build order

One scene. One useful response.

  1. Build the still page. Set the type, spacing, subject, and call to action. If that frame doesn’t work, fix it first.
  2. Choose the asset. Use an image for a fixed view or a model when the viewpoint must change. Confirm you can use the asset.
  3. Define one interaction. Write down what the visitor does and exactly what changes. “The product turns slightly with the pointer” is actionable. “Make it cinematic” isn’t enough.
  4. Connect scroll deliberately. Give the scene a start, a readable resting state, and an end. Keep normal navigation usable.
  5. Test the fallback. Check a narrow screen, touch input, keyboard navigation, reduced motion, and a failed graphics load. The content and main action must remain available.

Three.js’s responsive guide explains the rendering cost of higher resolution. GSAP’s matchMedia documentation covers adapting animation to viewport and motion preferences. Test your own page; a good reference is not evidence that your build is fast.

05 / Give your agent a real brief

Start with this prompt.

Attach your visual references and paste this into your coding agent from the project folder. It asks the agent to inspect what exists before choosing tools.

Build a responsive website with one purposeful 3D or depth interaction, using my attached images as visual references.

First inspect the source, dependencies, routes, and existing design. State what is already implemented. Do not infer a reference site's technology from its screenshot or claim its work as mine.

Keep the existing visual identity unless I ask for a redesign. Extract useful decisions from the references: typography, spacing, silhouette, layering, materials, and lighting. Make a strong still composition before adding motion.

Choose the smallest suitable approach: CSS and images for a fixed viewpoint, Three.js for a real model and camera, or the existing shader renderer for a shader effect. Reuse dependencies. Explain any new dependency before adding it.

If available, consult the installed GSAP, Animaxxing, or Animaxxing WebGL skills for the chosen effect. Verify their instructions and compatibility; do not claim they are installed without checking.

Define one clear pointer, touch, or scroll interaction and implement it. Keep real headings, links, and controls in HTML. Preserve keyboard access and normal navigation. Provide a readable still fallback if graphics fail, and respect reduced motion. Avoid continuous decorative animation when the scene is offscreen or the tab is hidden.

Use assets I supply or am permitted to use. Do not invent a model, creator credit, benchmark, or working feature. Ask for missing assets when they are essential.

Test desktop and narrow layouts, actual controls, touch behavior, reduced motion, and the graphics fallback. Report what you implemented and tested, and anything that remains unverified.

The takeaway

Make the response worth the render.

Start with a good page. Give the subject a clear role. Add movement that helps you feel its shape, understand the product, or move through the story. Keep it usable when that movement is gone.
